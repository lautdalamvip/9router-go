### 🚀 ci(workflows): publish the Docker image to `lautdalam/9router-go` on every push to main

- **Registry repointed.** `release.yml`'s `REGISTRY_IMAGE` and `ci.yml`'s new workflow-level `REGISTRY_IMAGE` are both `lautdalam/9router-go`. Nothing in `.github/` or `scripts/` still names `luqmenul/9router-go`.
- **New `docker-publish` job in `ci.yml`.** A push to `main` — which is what this workflow already triggers on — now builds and pushes multi-arch (`linux/amd64,linux/arm64`) to Docker Hub with three tags: `latest` (what a bare `docker pull` resolves, so it follows main), the branch name, and `sha-<short>` (the only tag never rewritten, so a running container stays traceable to a commit). Pushing to a repository that does not exist yet creates it.
- **Why a separate job rather than extra steps on the existing one.** The existing `docker` job is deliberately un-gated so a Dockerfile break stays visible on a PR whose tests are failing; that invariant is preserved, and its build is still `load: true` with no push. Publication is a different obligation, so it is its own job with `needs: [test, race, integration, docker]` — a job cannot gate itself, and putting a red commit on `latest` is how a broken gateway reaches whoever just pulled it.
- **Pull requests never publish.** `if: github.event_name == 'push'` on the job, not a branch-name test: a PR is unmerged code, and a PR opened from a fork is handed no secrets, so the login step could only ever fail there.
- **Two related identity bugs fixed, because the change would otherwise be half-done.** `scripts/notify-telegram.sh` told readers to `docker pull luqmenul/9router-go` and linked to `github.com/luqman-v1/9router-go/releases/tag/${TAG}` — but the release page is created in whichever repository ran the workflow, so from this fork the announcement both named an image the release did not write and linked to a release page that does not exist. The image now comes from `DOCKER_IMAGE`, which `release.yml` sets from `${{ env.REGISTRY_IMAGE }}` (single source of truth, cannot drift again), and the URL is derived from `GITHUB_REPOSITORY`. `release.yml`'s tag trigger and multi-arch build are unchanged.
- **Required setup, and it fails loudly if missing.** The fork needs two repository secrets: `DOCKERHUB_USERNAME` (= `lautdalam`) and `DOCKERHUB_TOKEN` (a Docker Hub access token with **Read & Write**). Without them the `docker-publish` job goes red on the next push to main — deliberately, rather than skipping in silence and leaving you believing images are being published when they are not.
- **Verified:** both workflows parse (`Bun.YAML.parse`) and a structural assertion run confirms every property above — registry value, `needs` list, `if` guard, `push: true`, the platform pair, all three tag rules, the preserved `load`-only verify build and its PGO assertion, and the notify step's `DOCKER_IMAGE` derivation. `sh -n scripts/notify-telegram.sh` passes and the derived values were printed back (`https://github.com/lautdalamvip/9router-go/releases/tag/v1.9.11`, `lautdalam/9router-go`).
- **Not yet done, and deliberately so:** the Dockerfile stages do not cross-compile (`web-builder` and `builder` run on the target platform instead of `--platform=$BUILDPLATFORM` with `GOARCH=$TARGETARCH`), so the arm64 half of each push is built under QEMU — minutes per push rather than seconds. Fixing that needs a Docker-capable machine to verify, which is why it is left out of this change.
